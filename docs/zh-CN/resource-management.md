# 资源管理权交接

[English](../en/resource-management.md)

团队中的工作区和会话可以转交管理权。接收者必须是同一团队的有效成员，并拥有可写团队角色；个人空间和项目不提供这个操作。项目管理继续由团队角色决定。

当前管理者打开资源的“共享…”面板，选择“转交管理权…”，搜索接收者，再确认转交。默认保留原管理者为可编辑协作者：可以查看、发送、停止和调整会话设置，但不能管理共享、删除或再次转交。接收者之后可以调整或撤销这项授权。取消“保留我为可编辑协作者”时不会新增原管理者的访问权，已有独立授权仍有效。

工作区交接同时改变随它继承管理权的会话；已单独转交的会话保持自己的管理者。会话可以单独交接，不会改变父工作区或其他会话。新会话继承当前工作区的管理归属；管理者主动分叉单独交接的会话时，新分叉由该管理者管理。

交接不会搬动目录、转移电脑或改写历史作者。Node 凭据、存储绑定、会话执行身份、已发生用量和已配置执行来源保持独立。接收者不会因此取得原账号的 Provider 凭据或插件安装权；全局执行配置仍由原账号或电脑所有者管理。现有共享规则保留。本操作不主动取消已接受的任务，后续执行仍检查当前授权；移除原管理者的访问权后，原账号模型或任务可能需要重新授权。

服务端检查管理版本。加载面板后若资源已被再次交接，过期请求不能覆盖新归属，需刷新后重新确认。同项目内接收者已经管理同名工作区时，先更改名称再交接。删除会话也会删除其单独管理归属，避免同一标识再次使用时继承错误权限。

共享数据库的 Server 实例必须使用同一版本。管理变化在同一事务产生权限通知，其他实例重新读取工作台和当前订阅的权限。这与跨 Server 的 Node 命令转发是不同能力；Node 路由仍遵循[架构说明](architecture.md#node-路由与事件)。

API 提供 `GET .../sharing/ownership` 读取管理者与版本、`GET .../sharing/ownership/candidates` 分页搜索接收者，以及 `PUT .../sharing/ownership` 提交交接。`...` 为 `/api/v1/workspaces/{workspace_id}` 或 `/api/v1/sessions/{session_id}`。提交字段如下：

```json
{
  "owner_user_id": "接收者的 user_id",
  "expected_owner_user_id": "当前管理者的 user_id",
  "expected_revision": 0,
  "retain_previous_owner": true
}
```

资源的 `access.owner_user_id` 表示当前管理者，`access.storage_user_id` 表示原存储／执行身份，`access.ownership_revision` 表示管理版本。`is_owner` 与 `is_execution_owner` 分别描述当前用户是否具备这两种身份，不可互相替代。
