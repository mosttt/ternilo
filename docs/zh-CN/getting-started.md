# 本地快速开始

本页带你在当前电脑启动 Ternilo、选择项目文件夹并完成第一次模型对话。只在本机使用时，安装 `ternilo` 即可，不需要数据库服务、Server、Worker 或登录账号。

需要统一管理多台电脑或 VPS，见[远程访问](remote-access.md)；需要为多人提供共享入口，见[服务器部署](deployment.md)。这两种情况都使用同一个 Server，不按机器位于本地还是云端区分版本。

## 1. 启动程序

如果已经收到针对当前系统构建的交付包，在解压目录打开终端，将包内 `bin/` 加入当前终端的 `PATH`，然后启动：

```bash
export PATH="$PWD/bin:$PATH"
ternilo serve
```

也可以直接执行 `./bin/ternilo serve`。手动启动的服务占用当前终端，保持终端打开；Ctrl-C 会正常停止服务。关闭浏览器不会停止这个进程。

打开终端打印的地址，默认是 `http://127.0.0.1:3210`，然后继续下面的第 2 步。若桌面应用已启动本地服务，先执行 `ternilo status` 查看地址，直接打开即可。

运行现成程序不需要 Rust 或 Node.js。文件搜索需要安装 `ripgrep`，并确保 `rg --version` 能在运行程序的环境中执行。Linux 上执行命令、后台任务或终端还需要安装 `bubblewrap`；浏览文件和配置模型不要求先搭建容器。交付包由维护者按[构建与打包说明](release-packaging.md)提供；还没有交付包时，可使用本页末尾的[源码启动步骤](#从源码启动)。

本地服务只接受当前电脑的连接：`--listen` 不能改为 `0.0.0.0`、局域网或公网地址。其他设备通过 `ternilo-server` 访问，由本机主动连接服务器；不需要开放电脑上的 `3210` 端口。

本机页面使用服务自动提供的临时访问令牌，不需要手动输入账号或模型 API Key。服务重启会更换这个令牌；页面会重新获取本机连接凭据，保留未发送草稿并恢复实时连接。恢复失败时先确认服务已启动，再重试连接或刷新页面；旧版页面偶发显示“连接 Ternilo 节点”时，也可刷新取得新令牌。新版就绪提示表示网页资源有更新，与模型密钥或 Server 账号登录无关。

## 2. 选择工作文件夹，开始会话

1. 点击“选择工作文件夹”，或侧边栏工作区旁的文件夹按钮。
2. 选择要交给 Agent 工作的项目目录。
3. 打开新会话；以后选中该工作区，再点“新会话”即可。

普通浏览器由后台服务检查填写的文件夹路径；桌面应用使用系统目录选择器。文件和终端操作以这个工作区为范围，访问工作区之外的位置受所选权限限制，交付物也归属于该会话。移除侧边栏中的工作区只移除登记，不会删除目录；已有会话进入“未分组”。

同一本机用户可以在多个会话中并行操作相同或重叠目录；这不会为各会话创建独立文件副本。需要避免并发写入冲突时，使用不同目录或工作树。通过 Server 共享电脑时，不同账号的重叠目录访问会等待目录空闲，详见[远程访问](remote-access.md#断线数据与权限)。

## 3. 配置 Provider、模型和 API Key

Provider 是一组模型服务连接设置，例如某家服务的 API 地址、Key 和模型列表。打开“设置 → 模型”，点击“添加 Provider”；通常只需添加一次，之后可以反复使用。

| 字段 | 示例 | 说明 |
|---|---|---|
| Provider ID | `my-provider` | 稳定小写标识；创建后不可改 |
| 显示名称 | `My Provider` | 工作台显示名称 |
| API 地址 | `https://api.example.com/v1` | API 根路径，不要填完整 `/chat/completions` 或 `/responses` |
| API 协议 | `openai-chat-completions` | 必须与端点真实协议一致；也支持 `openai-responses`、`deepseek-responses`、Gemini 的 `google-gemini` 和 Claude 的 `anthropic-messages`，地址与推理设置见[模型说明](models.md) |
| API Key | `sk-...` | 直接粘贴；无鉴权端点可留空 |
| 超时与重试 | 保持默认 | 按服务稳定性调整 |

在“Provider 默认模型设置”中填写服务提供的上下文窗口和最大输出 token，再在模型目录中填入真实 Model ID。模型支持推理强度时再展开相关选项；不确定厂商是否支持时，不必先启用。

同一 Provider 的模型若支持同一组推理强度，可以在默认设置中统一启用档位、选择默认档位并填写服务接受的值。例如把界面的 `high` 映射为服务要求的 `ultra`；未启用的档位不会显示或发送。

在“模型目录”中至少添加一个服务端真实 Model ID。上下文窗口、最大输出 token 和推理强度可以分别选择设置来源：

- “自动”：优先采用上游明确提供的这一项，否则继承 Provider 默认值；界面显示具体来源。
- “自定义”：仅覆盖这一项，其他字段继续自动取值；切回自动即可移除手动覆盖。
- 推理强度还可选“未启用”，明确不声明推理档位；上游没有返回推理配置不等于关闭。

上下文窗口用于显示占用比例；默认在估算上下文达到所选模型窗口的 80% 时触发自动压缩。模型没有声明上下文窗口时不会退回固定 token 阈值，仍可手动执行压缩。最大输出 token 和推理档位会进入实际模型请求。“获取可用模型”会保留上游明确提供的容量和档位，缺失项继承 Provider；再次获取可以刷新已有模型的上游信息，但不会覆盖名称或手动值。

保存后，API Key 输入框会清空。Key 单独保存，模型配置和会话导出不会包含它的明文；再次编辑时留空表示保留，填写新值表示替换。无需去“凭据”页重复配置模型 Key。

“获取可用模型”由后台服务请求 Provider 的模型目录，浏览器不会取得已保存的 API Key。若服务不提供模型目录 API，可以手工添加。

最后在输入框下方或“设置 → 模型 → 当前会话模型”中选择 Provider、模型和推理强度。没有可用模型时，工作台会保留草稿并提示配置，配置完成后再发送任务。

### “凭据与登录”页什么时候使用

大多数模型用户不需要它：

- “插件登录”用于插件声明的 OAuth、设备码或一次性授权流程。
- “本地命名凭据”用于非模型服务通过稳定引用取值。
- Provider 自动生成的凭据引用只显示状态，不需要手工维护。
- 同名非空环境变量优先且只读，网页不能覆盖或删除。

## 4. 验证真实模型

先发送一条简单任务，例如“列出这个项目的主要目录，并说明从哪里开始阅读”。如果只想验证模型连接，可以先问一个不需要工具的问题。正常时，对话页会逐步显示输出。

之后按需要检查工作区读取、停止和图片输入；“调用轨迹”保留模型与工具的详细过程、耗时和用量，排查问题时再打开。

| 错误 | 检查项 |
|---|---|
| `401` / `403` | API Key、账号权限、模型访问权限 |
| `404` | API 地址是否误含完整请求路径，或是否缺少服务要求的 `/v1` |
| `model not found` | Model ID 是否与服务端完全一致 |
| credential 未配置 | Provider 是否保存了 Key；环境变量是否为空或引用名不一致 |
| 响应格式不兼容 | Provider 选择的 Chat Completions、OpenAI Responses、DeepSeek Responses、Google Gemini 或 Claude Messages 协议是否与端点一致；原生端点不能按兼容协议调用 |
| timeout / retry exhausted | 网络、代理和服务地址是否可用，再按需调整超时与重试 |
| sandbox backend unavailable | Linux 是否安装 `bubblewrap`；其他系统是否使用了包含对应沙箱运行程序的交付包 |

不同厂商的 OpenAI-compatible 实现可能仍有差异。真实凭据验证应使用低成本请求，不要把 Key 粘贴到聊天、日志或仓库文件。

## 5. 数据与备份

默认数据目录：

- 设置了 `XDG_DATA_HOME`：`$XDG_DATA_HOME/ternilo`
- 未设置：`~/.local/share/ternilo`

这个目录保存工作区登记、会话历史、模型及插件配置、凭据、附件和定时任务。你选中的项目目录通常在它外面，项目源文件不会因为登记工作区就被搬进来。

备份时分别保存两部分：整个 Ternilo 数据目录，以及需要保留的实际项目目录。复制 Ternilo 数据前，用 `ternilo stop`（自定义目录加 `--data-dir`）停止后台服务并确认成功；使用该目录的 RPC/ACP 程序也要先结束。不要只复制某个 SQLite 文件，或把关闭浏览器、桌面窗口当作停止服务。

通过外部 Profile、环境变量或服务管理器提供的设置不一定在数据目录中。使用这些设置时，一并保存对应文件；连接 Server 的 Node 还需保存电脑 ID、连接地址及只显示一次的连接凭据。备份含私密配置和凭据，应限制访问。

恢复时，先停止目标数据目录的所有使用者，再把完整数据备份恢复到默认数据目录或新的空目录，并将项目文件恢复到原来的绝对路径。使用与备份匹配的程序版本；恢复到自定义位置时，启动、查询和停止都指定同一目录，例如：

```bash
ternilo serve --data-dir /path/to/restored-ternilo-data
```

恢复后检查工作区、历史会话、模型列表和凭据是否可用。本机网页访问令牌会重新生成，不需要备份旧令牌；远程 Node 的连接凭据不同，需要恢复启动配置，并确认 Server 显示该电脑在线。只有历史可读并不代表远程连接已恢复。Server 自身的数据另行备份，见[原生 Server 备份与恢复](server-reference.md#原生-server-备份与恢复)。

恢复历史不等于恢复正在运行的进程。异常退出时未结算的运行会在会话恢复时标记中断，已经开始但没有结果的工具调用标记为结果未知，不会自动重试外部操作。未完成的定时任务会按调度规则恢复；它们与重跑中断任务是不同机制。恢复后先检查历史及文件副作用，再决定是否重新提交。

## 查看、停止和重新启动

另开终端，在解压目录执行；以下命令使用默认数据目录：

```bash
./bin/ternilo status
./bin/ternilo stop
```

如果启动时指定了 `--data-dir`，这里也必须指定同一路径。已经安装到 `PATH` 时可以省略 `./bin/`。`status` 会显示实际地址；`stop` 成功返回表示任务已取消、应用完成收尾并释放数据目录，然后才能安全备份或重新启动。等待超过 30 秒仍未完成时会报错，应查看原服务日志。源码开发时可使用 `target/debug/ternilo status` / `stop`。

桌面应用可以连接这个服务，需使用同一用户、相同数据目录和匹配版本，并将服务监听地址保持为 `127.0.0.1`。打开桌面不会替换服务的 Profile 或启动参数；需要调整时先停止再启动。桌面安装包与命令行交付包分别提供，详见[桌面应用](desktop.md)。

## 可选启动参数

日常模型、插件和 Agent 预设在网页中设置。只有调整监听端口、数据目录、宿主限制或额外 Profile 时，才需要以下启动参数。

`ternilo` 不带子命令时等同于 `ternilo serve`，并且仍会读取下表环境变量。长期运行参数同时支持命令行和固定环境变量；同一项同时出现时，命令行优先：

| 命令行参数 | 环境变量 | 适用子命令与默认值 |
|---|---|---|
| `--listen ADDRESS` | `TERNILO_LOCAL_LISTEN` | `serve`；默认 `127.0.0.1:3210` |
| 可重复的 `--profile PATH` | `TERNILO_LOCAL_PROFILES` | `serve`、`run`、`rpc`、`acp`；环境变量用逗号分隔多个 JSON Profile 路径 |
| `--data-dir PATH` | `TERNILO_LOCAL_DATA_DIR` | `serve`、`status`、`stop`、`rpc`、`acp`；默认目录见[数据与备份](#5-数据与备份) |
| `--max-steps N` | `TERNILO_LOCAL_MAX_STEPS` | `serve`、`run`、`rpc`、`acp`；默认 `0`，表示管理员不额外限制 Agent 的执行步数 |

`run` 后面的任务文本和 `--json` 只用于本次命令，不读取环境变量。

端口被其他程序占用时，可以换一个回环端口，保留原数据目录：

```bash
ternilo serve --listen 127.0.0.1:3211
```

确实需要另一套独立环境时，再同时指定新的数据目录；它不会自动复制原环境的模型配置和会话：

```bash
ternilo serve \
  --listen 127.0.0.1:3211 \
  --data-dir /path/to/ternilo-data
```

同一个数据目录由一个后台服务持有，浏览器、桌面和远程入口可以共用。桌面已启动服务时，用 `ternilo status` 查看实际地址，无需再启动第二个 `serve`。需要手机远程连接时，在同一个 `ternilo serve` 上添加 `--gateway-url`、`--token` 和 `--node-id`，仍使用原来的会话、模型与插件；不要另开第二个进程争用数据目录。完整步骤见[远程访问](remote-access.md)。

## 从源码启动

Ternilo 把 [Linorun](https://github.com/mosttt/linorun) 作为相邻路径依赖，使用与当前 Ternilo 配套的版本并按以下布局放置源码：

```text
/path/to/source/
├── linorun/
└── ternilo/
```

需要：

- Rust 1.98.0；仓库的 `rust-toolchain.toml` 会让 rustup 自动安装或选择它。
- 首次构建时可访问 Rust crate registry。
- Linux 上需要执行命令、后台任务或终端时安装 `bubblewrap`。
- 文件搜索及相关集成测试需要 `ripgrep`（`rg` 命令）。
- 源码首次构建需要 Node.js 安装依赖并生成前端；运行已包含网页的程序不需要 Node.js。

从 Ternilo 仓库根目录启动：

```bash
rustc --version
npm --prefix web ci
npm --prefix web run build
cargo run --locked -p ternilo -- serve
```
