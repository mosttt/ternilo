# Server 发起客户端升级

Server 从官方 GitHub Release 获取并缓存指定稳定版客户端包，接入电脑经 Server 下载并独立验签，等待空闲后由本机更新器安装和重启；保留配置、数据目录、身份和凭据。范围首先是 browser／CLI 接入端，桌面安装版、容器替换和 Work 不在本阶段。

## 实施顺序与完成条件

1. 发行清单和签名：清单覆盖版本、平台、文件名、大小、SHA-256、最低客户端版本、Server 兼容范围与数据格式代次。Server／Node 内置同一公钥，私钥仅用于发行。正式 Release 必须在全部打包检查通过后签名。
2. 本机更新：所有者明确启用，记录安装位置及启动方式。包先下载验证，空闲检查覆盖对话、子任务、后台作业；进入维护后不接受新执行。独立更新器保留旧程序、协调正常停止和服务重启，数据代次不兼容的版本不进入自动安装。仅网络重连失败不触发程序回退。
3. Server 流程：所有者权限、发行包缓存、持久升级任务、按机器和包限定的短期下载授权；真实状态区分下载／等待空闲／安装／等待重连／完成／失败。支持单台及批量操作，重试不能重复执行已接受的升级。
4. 验收：签名／篡改／版本回退／路径边界；真实安装、重启与失败恢复；账号和机器隔离；Server 重启、Node 断线、运行中任务不被打断；中英韩界面、桌面和手机实际浏览器；对应使用及发行文档。

## 当前进度

正式更新使用专用 Ed25519 签名。GitHub `client-update-signing` 环境仅允许 `v*` 标签，私钥存入环境 Secret `TERNILO_UPDATE_SIGNING_KEY`，公钥位于 `crates/ternilo-update/release-public-key.txt`。共享验签／下载、Node 更新控制与独立更新器、Server 缓存与持久任务、单台／批量更新界面已完成，本阶段验收及完整 CI 已通过，PR #10 已合入 main，v0.2.23 已正式公开。六平台客户端清单公钥验签通过；公开产物与正式程序运行证据见[发行验收](release-0.2.23-acceptance.md)。

连接使用 Executor 协议 49，握手直接携带客户端版本、平台和升级能力／状态；机器升级使用独立 `ExecutorCommandBody::ClientUpdate` 分支，不混入会话应用 RPC。升级状态帧与控制命令共用 WebSocket，HTTPS 仅用于包下载。持久化旧 metadata 的缺省字段只保留已有记录可读，不作为旧连接协议兼容路径。首次启用必须成套升级 Server／Node。SQLite／PostgreSQL 继续复用组件迁移与租户隔离机制。

## 安装与恢复实现

本机安装布局明确分为普通解压目录和官网脚本的版本目录。官网布局将新版写到新的 `releases/<版本>-<平台>/bin`，保留旧版本文件，再替换原启动脚本中的程序地址与插件链接；不改变无参数打开浏览器的行为。安装锁、所有者记录和未完成标记位于稳定安装根，更新配置中的活动路径随激活切换。普通目录使用完整程序备份和文件交换。

正向激活与回退均受未完成标记保护。显式恢复从安装目录外的 helper 执行，避免 Windows 的执行文件占用。systemd helper 使用独立 transient scope，同步取得退出结果，并保留调用方的用户、组、环境和文件系统上下文，不依赖 `--system` 下默认以 root 创建的服务进程。新版本只有本机健康且 WebSocket 已连接时才报告完成，并为启动稍慢的情况继续检查。

所有者启用许可单独保存在 `config/client-updates-enabled.json`，与安装元数据分离，安装或恢复不会覆盖用户在执行期间的停用决定。Server 的幂等请求优先返回已有任务，即使电脑已更新或暂时离线，也不会重新下载安装。

## 空闲升级等待与 Supervisor 现场排查（2026-10-24）

用户将 Server 更新至 0.2.24 后，DMIT 的 0.2.23 客户端等待空闲超过半小时，确认无正在运行的任务。执行资源文件留有早于当前客户端启动的 `process-*` 记录，进程列表未见 Ternilo 子进程。registry 会保留重启前的归属记录，但无法重建完成观察器；原空闲检查将未知状态一直当作普通忙碌等待。修补后报告具体资源、会话和运行编号，不再将未知状态作为运行中任务持续等待，不自动删除记录，也不放宽账号撤销的清理要求。

Supervisor 另误用了组名 `ternilo`，实际进程名为 `ternilo:ternilo_00`。用户取消更新、修正完整名称，停止客户端后备份处理已核对的旧记录并重新启动。服务管理器归属校验现提前到客户端下载前，安装前仍复查。

之后的安装因健康检查超时回退。用户直接启动 0.2.24 能读取原数据并连接 Server，启动耗时几十秒。以官方归档和签名清单复现同目录安装／数据布局、完整 Supervisor 名称和 `startsecs=3`：正常流程约 6 秒完成；将新版启动延迟 45 秒，公开旧版更新器在约 33 秒回退并报告相同错误。启动确认现使用真实时间的 120 秒窗口，保留错误版本拒绝和超时回退。修正后的更新辅助程序在相同 45 秒延迟下完成安装、健康确认及重连，并释放操作锁。

另一台本机已实际运行 0.2.24 并在线，最近更新却记录安装锁冲突。只读检查确认当前版本、启用配置均为 0.2.24，只有当前服务持有正常共享锁。界面现明确说明“新版已正常运行，无需再次更新；上次自动更新未能正常确认结果”，保留原诊断。安装后的启动／连接提示和回退文案亦已修正，中英韩同步。

未知资源回归在修复前复现未知状态被作为忙碌等待，修复后三个维护门测试及账号清理未知状态测试通过；新增真实延迟 35 秒才注册健康服务的回归通过。更新窗口九项测试、类型检查、i18n、受影响模块 all-targets Clippy、Client／Server 构建及文档检查通过。当前内嵌 Web 的实际浏览器验收用三类状态夹具验证三语言、390×600 深色布局、无需展开诊断即可阅读的处理说明、固定可见操作与原始诊断，页面／控制台／HTTP 无意外错误；实际截图已检查。
