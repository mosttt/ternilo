# Server 发起客户端升级

用户确认的目标：Server 从官方 GitHub Release 获取并缓存指定稳定版客户端包，接入电脑经 Server 下载并独立验签，等待空闲后由本机更新器安装和重启；保留配置、数据目录、身份和凭据。范围首先是 browser／CLI 接入端，桌面安装版、容器替换和 Work 不在本阶段。

## 实施顺序与完成条件

1. 发行清单和签名：清单覆盖版本、平台、文件名、大小、SHA-256、最低客户端版本、Server 兼容范围与数据格式代次。Server／Node 内置同一公钥，私钥仅用于发行。正式 Release 必须在全部打包检查通过后签名。
2. 本机更新：所有者明确启用，记录安装位置及启动方式。包先下载验证，空闲检查覆盖对话、子任务、后台作业；进入维护后不接受新执行。独立更新器保留旧程序、协调正常停止和服务重启，数据代次不兼容的版本不进入自动安装。仅网络重连失败不触发程序回退。
3. Server 流程：所有者权限、发行包缓存、持久升级任务、按机器和包限定的短期下载授权；真实状态区分下载／等待空闲／安装／等待重连／完成／失败。支持单台及批量操作，重试不能重复执行已接受的升级。
4. 验收：签名／篡改／版本回退／路径边界；真实安装、重启与失败恢复；账号和机器隔离；Server 重启、Node 断线、运行中任务不被打断；中英韩界面、桌面和手机实际浏览器；对应使用及发行文档。

## 安装与恢复实现

本机安装布局明确分为普通解压目录和官网脚本的版本目录。官网布局将新版写到新的 `releases/<版本>-<平台>/bin`，保留旧版本文件，再替换原启动脚本中的程序地址与插件链接；不改变无参数打开浏览器的行为。安装锁、所有者记录和未完成标记位于稳定安装根，更新配置中的活动路径随激活切换。普通目录使用完整程序备份和文件交换。

正向激活与回退均受未完成标记保护。显式恢复从安装目录外的 helper 执行，避免 Windows 的执行文件占用。systemd helper 使用独立 transient unit，调用方通过 `--wait` 获取退出结果，不再用可能永久持有维护锁的无界状态轮询。新版本只有本机健康且 WebSocket 已连接时才报告完成，并为启动稍慢的情况继续检查。

所有者启用许可单独保存在 `config/client-updates-enabled.json`，与安装元数据分离，安装或恢复不会覆盖用户在执行期间的停用决定。Server 的幂等请求优先返回已有任务，即使电脑已更新或暂时离线，也不会重新下载安装。
