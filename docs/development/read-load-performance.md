# 并发读取与用量查询优化

2026-10-03：新增可复现的独立读取压测，覆盖状态、最近／较早历史和设备整月汇总，在线／离线各执行 1／8／32 并发。每次请求验证内容，记录延迟分布、吞吐量和错误；使用临时进程、合成日志及独立数据库，没有改动运行实例。通用执行方式见[性能验证](../zh-CN/performance.md)。

第一轮发现两个具体瓶颈：只读操作使用 SQLite `BEGIN IMMEDIATE` 竞争写锁；受限 PostgreSQL 对带 RLS 的 JSON 条件未得到预期索引收益，整月汇总重复扫描大量流式事件。默认 41612 事件／800 次模型尝试，在本机开发构建下 PostgreSQL 单并发汇总 p95 约 920 ms，32 并发离线汇总 p95 约 7762 ms，说明需要优化，不能将接口通过功能测试等同于容量验收。

已实现：

- 新增明确的只读事务入口：SQLite 使用读快照，PostgreSQL 使用只读事务；仅切换已核对的身份读取、资源权限、历史及设备用量读取。原有写事务继续提前取得 SQLite 写锁，避免读取后升级写锁的冲突。开放读快照与写入并行、读快照稳定性的测试已通过。
- Provider 开始／完成事件在同一日志写事务中批量投影到用量专用表，使用类型化的时间、调用位置和尝试字段；思考、提示词等事件不复制。首次建立投影读取已保存事实，原事件删除级联删除投影，权限沿用租户 RLS 与电脑所有权。汇总不再反复解析全部对话事件。
- 用量明细、分叉去重、迟到完成、删除及 RLS 合同继续验证；Control／Storage 回归通过。双库同负载第一轮复测均无错误，相关真实浏览器 5 项通过；最终并发发现合并的复测单独记录。

这一阶段只覆盖固定数据的并发读取，不宣称模型请求、写入、多主机接管或长时间稳定性已经通过压力测试。测试结果应连同构建模式与主机条件一起阅读。


对同时等候同一电脑资源发现的请求，共用已完成的发现结果，避免每个等待者再次请求同一快照。随后发起的刷新仍重新发现；资源修改使共享结果失效，失败／取消也不标记成功。没有按秒缓存或延迟撤权，返回工作台时仍读取当前资源权限。并发发现、后续刷新、失败重试和中间修改的单元测试已通过。

第一轮优化（只读事务＋用量投影）在同一台 i7-8550U、8 逻辑 CPU、开发构建（关闭调试信息）下测得：32 并发离线时，SQLite 混合读取约 66 → 148 请求／秒、状态 p95 约 1994 → 724 ms；PostgreSQL 混合读取约 9.9 → 90 请求／秒、汇总 p95 约 7762 → 401 ms。两库分别完成 5155／2717 次成功读取，错误为零。这些是本机诊断对比，不是生产容量；PostgreSQL 位于本机独立容器，客户端与服务端共享主机。


## 最终复测

包含并发发现合并的 `33b0533` 干净工作树，CLI／Server 均为 `dev` 构建且关闭调试信息；相同的 41612 原始事件／800 次尝试、每档约 10 秒、1／8／32 并发。SQLite 完成 5235 次成功请求，PostgreSQL 完成 2636 次，全部响应内容检查通过且无错误。完整原始测量（含程序 SHA-256、主机和样本数量）保留为 [SQLite](benchmarks/2026-10-03/sqlite-reads.json) 与 [PostgreSQL](benchmarks/2026-10-03/postgres-reads.json)。

| 32 并发场景 | 混合请求／秒 | 状态 p95 | 用量汇总 p95 |
|---|---:|---:|---:|
| SQLite，电脑在线 | 59.6 | 1016 ms | 139 ms |
| SQLite，电脑离线 | 152.3 | 797 ms | 154 ms |
| PostgreSQL，电脑在线 | 30.1 | 1236 ms | 395 ms |
| PostgreSQL，电脑离线 | 87.6 | 576 ms | 373 ms |

在线仍包含电脑发现、数据库和进程间通信成本；这组测试证明已定位瓶颈的改善与响应正确性，不宣称到达容量上限。后续需要发布构建、更多账号／电脑、写入与流式模型请求的独立负载，再形成部署规模建议。最终 SQL 条件已通过双库回归；相关真实浏览器 5 项及审批清理 10 项通过，延迟浮层问题另行修复后补验发行恢复。

## 较早 JSONL 历史页定位

2026-10-04：在 v0.2.0 标签之后继续优化本机／Node 的历史分页。过去每一页从文件末尾倒序扫描并解析所有比游标更新的事件；现在先在固定文件长度内按字节二分定位游标记录，再读取该页。没有新增磁盘索引或配置文件；最近页仍直接读尾部，顺序、页大小、游标与 Live 续接规则不变。游标边界和返回页继续校验连续序号；修复工具仍负责检查和修复完整规范日志。

对同一 30005 事件合成日志、同一台电脑、关闭调试信息的开发构建，预热后各 8 次实际 HTTP 测量，before_seq=1000／limit=200 的中位耗时 332.89 → 7.63 ms；before_seq=15000 为 168.96 → 7.69 ms；最近页约 8.05 → 7.20 ms。每次响应逐条对照原始事件。对照程序为本机保存的修改前开发二进制，历史分页源码与 v0.2.0 标签一致；原始样本、两个程序 SHA-256、测试补丁摘要及主机信息见 [history-seek.json](benchmarks/2026-10-04/history-seek.json)。此短时同机测量不是容量结论，也不代表其他历史／派生统计入口已全部优化。

3 项定向合同覆盖可变记录长度、超过 64 KiB 的 Unicode 记录、LF／CRLF、尾部无换行、日志追加、页首／页尾／越界游标及序号缺口。匹配 CLI／Server 构建、Clippy 通过；真实 Chromium 的本机／Server 两个长历史流程通过，包含整轮思考、缓存切换、Live 续接、手机布局及 Node 离线历史。首次本机完整长轮次显示 797 ms，返回缓存 234 ms，切回时没有再次 REST 读取历史。该实现尚未随 Release 发布，不改写 v0.2.0 标签。

后续复核补充：游标位于损坏日志的首条记录时，缺少序号 0 必须报错，不能因定位位置为文件开头返回空页；真正的空日志仍返回空历史。3 项分页合同及 Clippy 再次通过，性能样本保留其实际测量构建身份。

2026-10-04：较早历史定位优化已随 v0.2.3 发布；公开程序包与本机／Server 浏览器验收见[发行记录](release-0.2.3-acceptance.md)。此前 v0.2.0 标签保持原源码。
