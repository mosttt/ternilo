# Ternilo v0.2.30

## Per-model web access

Each model can inherit Provider defaults for search and fetch or override either independently. Account and device-local models share the same rules. External integrations still run on the execution computer with the existing credential authorization boundaries. Choices are consistently named Off, Model built-in, and External integration · service in Chinese, English and Korean.

Model-name allowlists no longer prevent built-in search, session creation or default-model selection. Provider support is determined when sending a request. An explicit upstream rejection keeps the input and session, shows an actionable error, and lets the user switch models. No silent downgrade or automatic duplicate paid request is made.

## Updates independent of task compatibility

An independently versioned maintenance channel keeps computers remotely upgradable when a later Server release changes the execution protocol. The computer displays Maintenance online, receives the update, and restores execution after installation. The existing client and independent installation helper perform the upgrade; no additional resident service is required. Enrollment identity, suspension and revocation remain enforced. Maintenance identity and the command mailbox survive Server restarts.

## Upgrade

**Manually upgrade Server and all connected computers to v0.2.30 for the initial rollout.** Earlier clients lack the maintenance channel; updating Server alone cannot add it. Let active tasks finish, update the complete client bundles using the existing installation method, then pull `ghcr.io/mosttt/ternilo-server:0.2.30` and recreate Server. Keep instance data, credentials, service arguments and enabled update settings. Do not delete computer registrations.

If the manual upgrade changes the binary directory, re-enable remote updates with the new binary and the existing restart method, then restart once to refresh installation registration.

This release uses execution protocol 51, maintenance protocol 1 and data epoch 1. The signed policy establishes client 0.2.30 as the maintenance baseline with Server `>=0.2.30, <0.3.0`; later execution-protocol changes alone will not raise that baseline. Data-epoch changes, incompatible maintenance protocols and stopped clients still require manual intervention.

See [web access](https://github.com/mosttt/ternilo/blob/v0.2.30/docs/en/web-access.md) and [client updates](https://github.com/mosttt/ternilo/blob/v0.2.30/docs/en/client-updates.md).
