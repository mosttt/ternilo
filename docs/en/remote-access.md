# Access computers and VPS instances remotely

Run `ternilo serve` on every execution computer and deploy one Ternilo Server as the authenticated entry point. Open Server from your phone or another computer to use the selected computer's workspaces, sessions, models and plugins. The execution computer makes an outbound WebSocket connection; its local port does not need port forwarding or public exposure.

Start with [Server deployment](deployment.md) or [Docker Compose](docker-compose.md). Native username/password authentication works without OIDC. Single-user mode restricts access to the instance owner; multi-user mode adds accounts and explicit resource sharing. Personal computers and personal VPS instances use the same connection procedure. A managed Worker is optional and is not required for personal computers.

## Register and connect a computer

1. Sign in to Server and open **User settings → My computers**.
2. Register a stable, distinct Node ID, such as `home`, `laptop` or `vps-01`.
3. Save the generated command and run it on that computer. Its credential is displayed only once.
4. Confirm that the computer is online in Server. Existing local workspaces and conversations are discovered; you can also choose a new directory on that computer.

```text
ternilo serve --gateway-url "wss://agent.example.com/api/v1/executors/connect" --node-id "home" --token "ter_n_REPLACE_WITH_YOUR_TOKEN"
```

The single-line command works in Bash, PowerShell and CMD. Replace the example token with the credential generated by Server. If a local service already uses this data directory, stop it first with `ternilo stop` (including `--data-dir` when customized), wait for completion, then restart with the same data directory and profile layers. Do not open the same data directory from two services.

A Node credential is for that computer's reconnects. Do not reuse another computer's or another account's credential. Revoke and register the computer again if the credential is lost or needs replacement.

## Multiple instances on one computer

Multiple instances can all connect to the same Server. Give each a different listening port, data directory, Node ID and credential. Register `home-a` and `home-b` separately, then run these commands in separate terminals:

```text
ternilo serve --listen 127.0.0.1:3210 --data-dir "./ternilo-data-a" --gateway-url "wss://agent.example.com/api/v1/executors/connect" --node-id "home-a" --token "ter_n_REPLACE_WITH_TOKEN_A"
ternilo serve --listen 127.0.0.1:3211 --data-dir "./ternilo-data-b" --gateway-url "wss://agent.example.com/api/v1/executors/connect" --node-id "home-b" --token "ter_n_REPLACE_WITH_TOKEN_B"
```

Relative directories are resolved from the current working directory; use fixed absolute paths for services. Open `http://127.0.0.1:3210` and `http://127.0.0.1:3211` for the respective local interfaces. Sessions, presets, models and credentials remain separate. Reconnecting the same Node identity replaces its earlier connection. Sharing an actual project directory is possible, but simultaneous changes by the same user can conflict; use separate directories or Git worktrees for independent tasks.

Specify the matching directory when inspecting or stopping an instance:

```text
ternilo status --data-dir "./ternilo-data-b"
ternilo stop --data-dir "./ternilo-data-b"
```

The desktop application's single-instance window behavior is separate from CLI service instances. Launching the desktop icon twice does not automatically create another independent Node.

## Local and remote access

Local Ternilo listens on loopback only, normally `127.0.0.1:3210`. Other devices use Server's authenticated URL. `0.0.0.0` is a bind address, not a destination to enter in clients. Plain HTTP on a LAN supports the basic workbench and native login, but PWA installation, some clipboard features and OIDC require a secure browser context. Use HTTPS/WSS for normal remote operation.

Folder selection in Server browses the selected execution computer, not the phone or browser's filesystem. Computer-scoped configuration stays there; account and platform models are configured on Server. Choosing an execution computer and choosing a model source are independent decisions.

Native browser login is stored for the current tab. Sign out through the sidebar. OIDC can be explicitly linked to an existing native account; accounts are not merged solely because their emails match. A PWA caches the public shell, not an offline execution environment.

## Long-running services

Every service option supports an environment variable; explicit CLI arguments take precedence. A Linux user service can read a private `0600` environment file:

```dotenv
TERNILO_LOCAL_GATEWAY_URL=wss://agent.example.com/api/v1/executors/connect
TERNILO_LOCAL_TOKEN=replace-with-your-computer-token
TERNILO_LOCAL_NODE_ID=home
TERNILO_LOCAL_DATA_DIR=/path/to/ternilo-data
TERNILO_LOCAL_LISTEN=127.0.0.1:3210
```

Set the systemd service's `ExecStart` to the installed `ternilo serve` command and `EnvironmentFile` to this file. Keep custom data and profile settings consistent with manual launches. Configure restart policy, shutdown timeout and user lingering according to the host's operational policy. A service does not automatically inherit temporary variables from your interactive terminal.

Use the service manager to stop managed instances; use Ctrl-C or `ternilo stop` for manually launched services. Normal shutdown stops admission, cancels interactive waits, persists results and releases the data directory after accepted work has settled. A network disconnect does not itself cancel an accepted command. Avoid force-killing a process as a substitute for graceful shutdown.

`--no-local-web` disables the local browser shell but leaves the authenticated management API. `--profile` accepts additional profile layers. `--max-steps` and `--max-tool-calls` set host ceilings, with zero meaning no host ceiling. For loopback development only, a `ws://127.0.0.1:4321/api/v1/executors/connect` URL requires `--allow-insecure-gateway`.

## Reconnection, permissions and recovery

Server retains received metadata and history for offline viewing, while execution and computer settings require the Node to be online. Project files remain on the computer. Separate Nodes can have identical internal session IDs without merging their histories. Server backups do not include those computers' local data or project files.

Durable command results prevent replay after ordinary reconnects. A process crash can leave the outcome of an external operation uncertain; inspect the files and session before retrying. Server can read the data it routes and is not an end-to-end encrypted blind relay. Remote actions retain the target session's permissions and approval rules. Granting submission access does not create another operating-system sandbox.

If Server opens but the computer is offline, inspect `ternilo status`, the gateway URL, credential and process logs. Proxies must forward WebSocket upgrades and avoid stream buffering. A busy data directory means another local service already owns it. Login denied in single-user mode means only the owner is currently admitted. See [deployment and recovery](deployment.md) and [local backups](getting-started.md).
